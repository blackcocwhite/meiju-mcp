## v0.2.0 发布前 Windows 修复：2026-10-14

首次推送后的 [CI](https://github.com/blackcocwhite/meiju-mcp/actions/runs/38496542349) 中，Linux Python 3.11/3.13 和 macOS Python 3.13 通过，Windows Python 3.13 为 272 项通过、4 项失败：登录静态资源使用默认系统编码读取，中文内容解码失败后被转换为 HTTP 503。

新增 6 个本机 HTTP 回归场景（3 个资源 × cp1252/GBK 两种默认编码）后，旧代码为 4 项失败、2 项通过；显式使用 UTF-8 修复后 6 项全部通过，完整本机套件 282 项通过，Ruff 检查和格式检查通过。该修复改变了资源读取编码，所以上一节“6 个模块 AST 一致”的结论仅适用于首次构建，不适用于修复后的版本。

修复提交 `3738f1d` 的[跨平台 CI](https://github.com/blackcocwhite/meiju-mcp/actions/runs/38497051636)已通过。它验证离线测试及本机回环流程，不验证各系统上的真实美居账号或物理空调控制。

Release 尚处于草稿阶段时，经维护者确认更新 v0.2.0 标签和附件，原始本地包保留备份。最终提交、附件校验值与各平台 CI 结果以 Release 的构建清单和 [Actions](https://github.com/blackcocwhite/meiju-mcp/actions) 为准；没有为了验收重启已登录的 MCP 或操作空调。

## Codex 原生对话验收：2026-10-14

安装说明修订并推送后，新建独立的本机 Codex 聊天。它使用已安装的个人 Skill 与本机 MCP 配置，由客户端提供原生工具；这不是全新操作系统或全新 Codex 账号。此前三个干净虚拟环境的安装检查与本节的客户端验收分开看待。

首次请求为普通的“查看我现在的美居设备列表”，没有显式指定 `$meiju-control`。记录显示 Agent 自行选用并读取该 Skill，随后出现真正的 `server: meiju` 原生工具调用。没有通过终端另启 MCP 或手工 JSON-RPC 替代原生调用。

| 验收项 | 实际结果 |
| --- | --- |
| 工具发现 | 新聊天可见全部 7 个 `mcp__meiju__` 工具 |
| 初始登录状态 | 原生 `meiju_login_status` 返回未登录，`meiju_login` 创建新的本机页面 |
| 用户手动登录 | 用户只在新页面输入凭据；继续同一聊天后确认登录成功 |
| 设备列表 | 原生 `meiju_list_devices` 读取到 1 台在线空调，型号与既有实测一致 |
| 连续温度查询 | 普通追问触发列表刷新及原生 `meiju_get_status`，分别报告室温、设定温度与电源状态 |
| 能力查询 | 原生 `meiju_get_capabilities` 返回候选控制范围，并说明实验性边界 |
| 零匹配目标 | 询问不存在的客厅设备时，报告未找到，没有用卧室温度替代 |
| 会话复用与隔离 | 新 MCP 进程在连续多轮查询中保持同一监听进程；旧登录进程保持原 PID 和监听端口，未被退出或重启 |

实际执行的原生工具为登录状态、登录入口、设备列表、状态和能力这 5 个。控制与退出工具只确认已发现，本轮没有执行，也没有复制其他进程或旧 App 的凭据。原先开关机真机证据仍属于前面的独立记录，不能当作本次原生控制验收。
