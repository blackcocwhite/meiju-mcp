# Stable profile identity and migration

Go profiles use a private `profile.json` with `version: 1` and a 32-character lowercase hexadecimal `vault_id`. Fresh profiles receive a random ID. Explicit migration retains the legacy path-derived ID so existing credential entries and ciphertext remain usable. The ID is a locator, not a token or encryption key.

`vault-backend.json` version 2 requires a valid identity file. Legacy version 1 profiles retain their path-derived behavior until explicitly migrated. Missing/damaged identities and incomplete migrations fail closed; they do not fall back to new keys.

## Procedure

Use a private, absolute destination that does not yet exist. Stop only the source profile's shared service and wait for in-flight requests to finish. Do not call account logout to stop a service.

```sh
meiju-mcp migrate-profile --session-dir /absolute/source --destination /absolute/destination
```

The command:

1. Rejects overlapping paths, unsafe permissions/links, a busy source and an existing destination.
2. Acquires source daemon, client and session locks; creates missing lock files if needed.
3. Copies encrypted session bytes, revision and client authorization/revocation records without invoking a credential store, decrypting tokens, enrolling clients or changing source payloads.
4. Writes the stable identity and version-2 backend marker. A `migration.pending` file prevents normal clients from using a partial copy.
5. Syncs files before clearing the pending marker. Endpoints, process metadata, certificates and restart budgets are regenerated by the destination service.

The helper's installed path, binary, signature, namespace and existing ACLs are unchanged. Do not re-sign it as part of ordinary relocation.

Update the service command, App connection JSON and Agent bridge arguments to the new profile. Rebuild Python virtual environments if their launch scripts/editable paths still point at an old source checkout; preserve the selected Python/Go implementation unless a switch is explicitly intended. Update installed Skill links separately.

## Acceptance

Start one destination service. Check `authenticated`, `persistence_status: saved` and `session_source: restored`, then list devices to validate cloud authorization and obtain fresh device IDs. Test both client identities and the read-only App. Restart only that service once more and repeat read-only validation.

A migrated file alone is not proof of a valid cloud login. Storage authorization errors are not token expiry; explain them before attempting any explicit authorization or new login.

## Failure and rollback

The source remains available as a rollback copy, but only one service should write a given saved-account identity. Do not run the source and destination as simultaneous writers.

A failed copy leaves its destination for diagnosis. `migration.pending` makes it unusable, and retries will refuse to overwrite it. Preserve the failed target, determine the failed phase, and use a new empty target or an explicit operator recovery. Do not silently delete or reuse partial state.

Before a later rollback, stop the active service and capture its latest consistent state. Do not replace newer login, logout or authorization changes with a stale backup, or resurrect an explicitly forgotten login. A legacy backup moved to a different path needs its original path restored or an explicitly preserved stable identity before credential lookup can work.

Restore the chosen encrypted state and matching configuration/binary, then validate it read-only. Removing a backup must not call logout/forget or delete keys still used by an active profile.

## Local-only files

Runtime profiles, virtual environments, client configuration, diagnostic output and rollback backups must be private and ignored by Git. The repository uses `.local` and `.cache` for development outputs; these paths are not public package contents or portable deployment defaults. Host-specific examples and local acceptance records should stay outside committed documentation.
